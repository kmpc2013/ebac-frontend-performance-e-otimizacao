2. CSS inteiro inline no <head>

Todo <link rel="stylesheet"> no <head> bloqueia a primeira pintura: o navegador não pinta nada até baixar e aplicar o CSS. Com o CSS externo, a ordem era: baixa o HTML → descobre o output.css → nova ida e volta na rede → pinta. Colocando o CSS dentro do HTML, essa segunda ida e volta deixa de existir.

Como foi feito: no build, não à mão

O src/index.html (fonte legível) continua com o <link>, o que é ótimo para desenvolver. O script de build troca o link pelo conteúdo do CSS na hora de gerar o index.html publicado:

scripts/build-html.mjs (trecho real, commit 9f2c305)
const fonte = readFileSync('src/index.html', 'utf8');
const css = readFileSync('src/output.css', 'utf8');

// CSS crítico inline: o CSS inteiro tem ~3,5 KB com gzip, então embuti-lo no HTML elimina
// a única requisição que bloqueava a renderização sem pesar no documento.
const LINK_CSS = '<link rel="stylesheet" href="src/output.css">';
if (!fonte.includes(LINK_CSS)) throw new Error(`src/index.html precisa conter ${LINK_CSS}`);
const comCssInline = fonte.replace(LINK_CSS, () => `<style>${css}</style>`);

const html = await minify(comCssInline, { collapseWhitespace: true, minifyCSS: true, ... });
writeFileSync('index.html', html);
Dois detalhes que valem ouro: o throw faz o build falhar alto se alguém mudar o <link> (sem ele, o CSS sumiria em silêncio e a página ficaria sem estilo). E o replace(LINK_CSS, () => …) usa uma função como substituto: com uma string, sequências como $& dentro do CSS seriam interpretadas como padrões especiais do replace.

$ npm run build

Quando o CSS inteiro inline faz sentido (e quando não)

✅ Faz sentido

  • CSS pequeno (aqui: 3,5 KB gzip, cabe com folga nos primeiros pacotes da resposta).
  • Página única: não há outra página para reaproveitar o CSS do cache.
  • Visitas são, em maioria, a primeira (landing page de campanha).

❌ Não faz sentido

  • Site com muitas páginas: o CSS externo é baixado uma vez e fica no cache; inline, ele é rebaixado em todo HTML.
  • CSS grande (dezenas de KB): o HTML incha e atrasa tudo. Aí o certo é só o CSS crítico (o da primeira tela) inline e o resto carregado sem bloquear.
  • Política de segurança (CSP) que proíbe <style> inline sem hash/nonce.

O custo honesto: numa revisita, o Pet&Style rebaixa 3,5 KB de CSS junto com o HTML, que antes viria do cache. Para uma landing page de ~5,8 KB, é uma troca que vale.

Seja honesto com o número medido. No comparativo final, o FCP melhorou de verdade: Mobile 1,11 → 0,68 s, Desktop 0,30 → 0,19 s. Mas atribuir esse ganho a cada etapa é arriscado: entre as medições por etapa, o FCP Mobile foi 1,01 → 0,93 → 0,90 s (imagens → minificação → CSS inline) e só caiu para 0,68 s na medição final, cujos commits extras mexeram apenas em contraste e num comentário. Ou seja, parte da diferença é ruído entre execuções. Com o servidor na sua máquina, o CSS de 4 KB já era barato (o Lighthouse estimava 171 a 198 ms de bloqueio no “antes”). O ganho do inline é estrutural (uma dependência de rede a menos no caminho crítico) e aparece mais com latência real, como no GitHub Pages. No README, escreva exatamente isso, sem inflar o resultado.

Favicon: por que um 404 derruba “Boas práticas”

Sem nenhuma tag, o navegador pede /favicon.ico por conta própria. No baseline, isso gerava uma requisição 404 e a mensagem Failed to load resource no console. O Lighthouse reprova a auditoria Browser errors were logged to the console, e Boas práticas fica em 96.

O ícone é gerado a partir do logo original, no mesmo script das imagens, sem passo manual:

scripts/images.mjs (trecho real)
const logo = lerOriginal('assets/logo.png');      // lido da tag antes
await sharp(logo).resize(72, 72).webp({ quality: 85 }).toFile('assets/logo-72.webp');
await sharp(logo).resize(32, 32).png({ palette: true }).toFile('assets/favicon.png');  // 1,5 KB

PNG 32×32 com paleta: 1,5 KB, suportado por todos os navegadores atuais. .ico só é necessário para navegadores muito antigos.

Meta description: o texto do resultado de busca

Sem ela, o buscador inventa um trecho a partir da página. A auditoria Document does not have a meta description derrubava o SEO para 91. Boa prática: 1 ou 2 frases, até ~155 caracteres, descrevendo a página para um humano (não uma lista de palavras-chave).

Como conferir: Console sem nenhum erro vermelho após Ctrl+Shift+R; Network com favicon.png 200; Lighthouse com Boas práticas e SEO em 100. Anote os números na fase 10.

5. Preload da imagem do LCP: por que não fizemos

O plano dizia: “preload da imagem do LCP, se o LCP ainda estiver alto”. Um <link rel="preload"> serve para avisar o navegador, o mais cedo possível, de um recurso que ele só descobriria tarde. A pergunta certa é: o hero é descoberto tarde?

Não. O <img> do hero está escrito no HTML inicial. O navegador tem um preload scanner: enquanto o parser principal trabalha, um leitor secundário varre o HTML que chegou e já dispara o download de imagens, CSS e scripts que encontra. E o hero ainda tem fetchpriority="high":

  <img src="assets/produtos/hero-800.webp" srcset="..." sizes="..."
       width="1080" height="720" fetchpriority="high" alt="...">
</picture>

Como confirmar com dados: no Lighthouse do “depois”, abra o LCP breakdown. Se o load delay (tempo entre o HTML e o início do download do hero) for pequeno, preload não tem o que ganhar. Anote esse número: ele é a justificativa da decisão no README.
No relatório depois-mobile-2 deste repositório (a execução mediana): TTFB 9 ms · load delay 9 ms · load duration 5 ms · render delay 145 ms (tempos observados no trace, sem a simulação de rede). O download do hero começa praticamente junto com o HTML; a maior fatia agora é o render delay, que preload nenhum resolveria.

6. Contraste: o laranja que reprovava

A auditoria Background and foreground colors do not have a sufficient contrast ratio (color-contrast) segurava a Acessibilidade em 94. A WCAG exige razão de contraste mínima de 4,5:1 para texto normal e 3:1 para texto grande (≥ 24 px, ou ≥ 18,66 px em negrito). O orange-500 sobre branco dava 2,88:1.

7. Publicar no GitHub Pages e rodar o PageSpeed Insights

Este passo é seu: ele depende da sua conta no GitHub e é uma ação externa (publica o site na internet). O código já está pronto para isso: o index.html gerado fica na raiz e todos os caminhos são relativos (assets/…).

  1. Confirme que o index.html da raiz está atualizado: rode npm run build e veja se o git status fica limpo. O GitHub Pages publica arquivos, não roda o seu build.
  2. Faça o push da branch main para um repositório público (a entrega da fase 12 já exige isso).
  3. No repositório: Settings → Pages. Em Build and deployment → Source: Deploy from a branch. Branch: main, pasta: / (root) → Save.
  4. Aguarde 1 a 2 minutos (a aba Actions mostra o deploy). O endereço aparece no topo da página de Pages: https://<seu-usuario>.github.io/<repositorio>/.
  5. Abra o endereço e confira: imagens carregando, Console sem erros, Network sem 404.
  6. Acesse pagespeed.web.dev, cole o endereço e clique em Analisar. Salve prints das abas Celular e Computador em docs/relatorios/depois/.
Detalhe do Jekyll: o GitHub Pages processa o repositório com Jekyll, que ignora arquivos e pastas que começam com _. Não é o caso aqui, mas se algo “sumir” na publicação, um arquivo vazio chamado .nojekyll na raiz desliga esse processamento.

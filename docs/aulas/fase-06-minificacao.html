Minificação de HTML e CSS

Hoje cuidamos das fichas G4 e G5: tirar dos arquivos de texto tudo o que só serve a humanos. É obrigatório no enunciado, é rápido, e vai ensinar uma lição importante: medir o ganho real, que é bem menor do que parece quando o servidor já usa gzip.

1. Minificar não é comprimir

As duas técnicas reduzem bytes de texto, mas em momentos e de jeitos diferentes. E elas se sobrepõem, o que explica os números da seção 6.

✂️ Minificação

no build, uma vez
Reescreve o arquivo removendo o que o navegador não precisa: indentação, quebras de linha, comentários, aspas e atributos redundantes. O resultado continua sendo HTML/CSS válido, só que ilegível.

🗜️ Compressão (gzip, Brotli)

no servidor, a cada resposta
Codifica os bytes para a viagem e o navegador decodifica na chegada. Funciona muito bem em texto repetitivo, e espaço em branco e nomes de classe repetidos são exatamente isso.

2. O CSS: --minify e o escopo da varredura

O CSS do Tailwind é gerado: a CLI lê seus arquivos, encontra os nomes de classe e escreve só as regras usadas. Minificar é uma flag. O package.json ficou assim:

package.json (scripts)
"build:css": "tailwindcss -i ./src/input.css -o ./src/output.css --minify",
"build:html": "node scripts/build-html.mjs",
"build": "npm run build:css && npm run build:html"

A armadilha anunciada na fase 4

O Tailwind v4 tem detecção automática de fontes: sem configuração, ele varre a pasta do projeto inteira (respeitando o .gitignore) atrás de qualquer texto que pareça classe. Só que agora o projeto tem docs/aulas/, com HTMLs cheios de palavras como card, grid, flex, hidden…

Fiz o experimento: gerei o CSS minificado com a detecção automática ligada, com a pasta docs/ do jeito que ela está hoje.

Versão do output.cssBrutogzip
Antes (sem minificar, tag antes)16,9 KB3,8 KB
Minificado, varrendo o projeto todo (inclui docs/)18,0 KB4,4 KB
Minificado, varrendo só o index.html13,5 KB3,5 KB
Leia de novo a linha do meio: minificado e maior que o original sem minificar. As classes das aulas viraram regras de CSS que a landing page nunca usa. Os números do meio variam conforme o conteúdo de docs/ cresce.

A correção fica no src/input.css:

src/input.css
- @import "tailwindcss";
+ @import "tailwindcss" source(none);

  /* Só o HTML da página gera classes. Sem isso, a detecção automática do Tailwind v4
     varreria a pasta inteira (inclusive docs/aulas) e colocaria classes extras no CSS. */
+ @source "./index.html";
PeçaO que faz
source(none)Desliga a detecção automática. Sem nenhuma fonte, o Tailwind não geraria utilitário nenhum.
@source "./index.html"Lista explicitamente a única fonte. O caminho é relativo ao input.css: aponta para src/index.html, a fonte legível (seção 3).
AlternativaManter a detecção e excluir só a pasta: @source not "../docs";. Funciona, mas é uma lista de exclusões que cresce. A lista de inclusões (“só isto”) é mais previsível.
Verifique antes de afirmar (de novo): depois de regerar, comparei as classes do HTML com as regras do CSS. Todas as classes usadas continuam lá. E as duas variáveis sem uso que a fase 4 encontrou, --color-amber-600 e --color-blue-300, sumiram: elas vinham de algum arquivo fora da página que a detecção automática tinha lido. O “código morto” da G4 era, na verdade, um problema de escopo da varredura.

3. O HTML: fonte legível e arquivo gerado

Com o CSS, o arquivo gerado já era separado da fonte. Com o HTML, não: o index.html era, ao mesmo tempo, o arquivo que você edita e o que o navegador baixa. Minificar ele no lugar deixaria o projeto impossível de manter. A solução é a mesma do CSS: separar fonte e saída.

projeto/ ├── index.html # GERADO por npm run build: não edite ├── src/ │ ├── index.html # fonte legível: é aqui que você edita │ ├── input.css │ └── output.css # GERADO pela CLI do Tailwind └── scripts/ ├── images.mjs # fase 5 └── build-html.mjs # minifica src/index.html → index.html

O index.html continua na raiz porque é ele que o serve (e o GitHub Pages) entrega em /. Os caminhos dentro de src/index.html (src/output.css, assets/…) são escritos pensando na raiz, onde o arquivo final mora. A fonte abre com um comentário avisando isso, e o próprio minificador remove esse comentário da saída.

scripts/build-html.mjs (versão da fase 6)
import { readFileSync, statSync, writeFileSync } from 'node:fs';
import { gzipSync } from 'node:zlib';
import { minify } from 'html-minifier-terser';

const fonte = readFileSync('src/index.html', 'utf8');

const html = await minify(fonte, {
  collapseWhitespace: true,
  conservativeCollapse: true, // mantém um espaço entre elementos inline (ex.: logo + "Pet&Style")
  removeComments: true,
  removeRedundantAttributes: true,
  removeScriptTypeAttributes: true,
  removeStyleLinkTypeAttributes: true,
  useShortDoctype: true,
  minifyCSS: true,
});

writeFileSync('index.html', html);

// imprime bruto e gzip, para você registrar no README
const kb = (bytes) => `${(bytes / 1024).toFixed(1)} KB`;
const tamanho = (texto) => `${kb(Buffer.byteLength(texto))} (gzip ${kb(gzipSync(texto).length)})`;
console.log(`src/index.html  ${tamanho(fonte)}`);
console.log(`index.html      ${tamanho(html)}`);
OpçãoO que remove
collapseWhitespaceIndentação e quebras de linha entre tags. É de onde vem quase todo o ganho.
conservativeCollapseModera a opção acima: reduz espaços a um, nunca a zero. Seção 4.
removeComments<!-- … -->, como o aviso no topo da fonte.
removeRedundantAttributesAtributos com o valor padrão (ex.: type="text" em <input>).
removeScriptTypeAttributes / removeStyleLinkTypeAttributestype="text/javascript" e type="text/css", que já são o padrão.
useShortDoctypeGarante o <!doctype html> curto.
minifyCSSCSS dentro de <style> e de atributos style. Hoje não há nenhum; na fase 9 vai haver (spoiler no fim da seção 6).
Ficou de fora, de propósito: removeAttributeQuotes e removeOptionalTags. Economizam poucos bytes a mais, que o gzip já comprime quase de graça, e tornam o HTML gerado mais frágil e mais difícil de depurar.

Novo hábito: toda mudança no HTML agora é em src/index.html, seguida de npm run build. Se você editar o index.html da raiz, a próxima build apaga a sua mudança sem aviso. E faça commit dos dois: a fonte e o arquivo gerado (é o gerado que o GitHub Pages publica).

4. Por que conservativeCollapse?

Espaço em branco entre tags às vezes importa. Entre dois elementos que ficam lado a lado na mesma linha, o espaço do código vira um espaço na tela. O minificador decide o que é seguro remover olhando o nome das tags, mas ele não lê o seu CSS: não sabe que uma tag virou inline-block. Quando ele erra, dois elementos ficam colados.

Fonte

Minificado

Simulação: com a opção desligada, o espaço entre as tags é removido por completo. Com ela ligada, sobra um espaço: custa um byte e não muda nada na tela.

No Pet&Style, o <a> do logo é flex com gap-2, então o espaço entre o <img> e o texto “Pet&Style” nem chega a aparecer. A opção está ali como seguro: se alguém trocar o flex amanhã, o layout não quebra só na versão minificada. Bug que só aparece no arquivo gerado é dos mais difíceis de achar.

6. Números honestos

  
O que entra no README é o que o visitante transfere, ou seja, a coluna do gzip.

“HTML antes” é a fonte depois da fase 5: os <picture> com srcset fizeram o HTML crescer de 9,9 KB (a medição da fase 3) para 12,6 KB. Minificado, ele termina em 9,6 KB: menor que o original, mesmo carregando muito mais informação.

  

  


  
Por que o ganho com gzip é tão pequeno?

  
O gzip funciona trocando trechos repetidos por uma referência curta (“repita os 16 caracteres de 40 posições atrás”). Uma indentação de 16 espaços que aparece em cada linha é a coisa mais repetitiva que existe: depois da primeira vez, cada repetição custa poucos bits. A minificação remove, antes, justamente o que o gzip já comprimia bem. As duas técnicas atacam o mesmo desperdício.

  
Compare com a fase 5: o hero sozinho caiu de 160,4 KB para 18,0 KB, uma economia de ~142 KB. A minificação inteira economizou ~0,7 KB transferido: cerca de 200 vezes menos. Por isso a ordem de prioridade da fase 4 (imagens primeiro, texto “de brinde”) estava certa. Escreva isso no README com os números: avaliação honesta vale mais que porcentagem bonita.

  
Então para que minificar? Custa zero em tempo de execução, nem todo servidor comprime (um bucket mal configurado entrega texto cru), o navegador lê menos bytes para analisar, e o enunciado pede. E o maior ganho de CSS desta fase nem veio da minificação: veio de não gerar regras desnecessárias (o escopo da varredura, seção 2).

  
🔭 Gancho para a fase 9: o CSS inteiro tem só ~3,5 KB com gzip, mas é uma requisição separada que bloqueia a primeira pintura. Na fase 9, o build-html.mjs vai passar a colocar esse CSS dentro do HTML, num <style>, e é aí que a opção minifyCSS começa a trabalhar.







  
7. Conferir a compressão no servidor

  
Os números de gzip acima foram calculados pelo script. Falta provar que o servidor realmente comprime. O serve faz isso por padrão:

  
    
    
  1. npx serve ., janela anônima, DevTools → Network com Disable cache.
    2. 
    
  2. Recarregue. Ative ⚙️ → Big request rows: a coluna Size passa a mostrar duas linhas, a de cima é o transferido e a de baixo é o tamanho real.
    3. 
    
  3. Clique no documento (localhost) e depois no output.css → aba Headers.
    4. 
    
  4. Em Request Headers, o navegador anuncia o que aceita (accept-encoding). Em Response Headers, o servidor diz o que usou (content-encoding).
    5.

Ilustração. O transferido fica um pouco acima do gzip calculado por causa dos cabeçalhos HTTP. Repare na imagem: transferido ≥ real. AVIF já é comprimido e o serve nem tenta comprimir de novo, assim como acontecia com o JPG na fase 3.

  
O navegador aceita br (Brotli), que comprime texto um pouco melhor que o gzip, mas o serve responde com gzip. O GitHub Pages e a maioria das CDNs já entregam Brotli. Se você publicar lá (bônus), confira esse header de novo. Se já estiver no código da fase 9, não haverá requisição do output.css: o CSS estará dentro do documento; confira o content-encoding do próprio localhost.

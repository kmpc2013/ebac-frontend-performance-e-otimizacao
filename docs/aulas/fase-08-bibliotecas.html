1. Quanto custa uma biblioteca de verdade

Imagem e JavaScript de mesmo tamanho não custam o mesmo. A imagem é baixada e decodificada (em geral fora da thread principal). O JavaScript é baixado, analisado, compilado e executado na thread principal, que é a mesma que responde a cliques e pinta a tela.

flowchart LR
  D["📶 Download
pesa em LCP/FCP
se bloquear"] --> P["🧩 Parse e compile"]
  P --> E["⚙️ Execução"]
  E --> T["🧵 Thread principal ocupada"]
  T --> TBT["TBT
no laboratório"]
  T --> INP["INP
no usuário real"]
  style T fill:#d93025,color:#fff,stroke:#d93025
Um <script> no <head> sem defer/async ainda bloqueia o parser: o HTML para até o script ser baixado e executado.
Curiosidade do nosso baseline: o Pet&Style não tem nenhum script, mas o TBT Mobile (mediana) foi 27 ms no “antes”, e não zero (uma das 3 execuções deu 63 ms; numa etapa intermediária, a mediana chegou a 170 ms). No “depois” ficou em 0 ms, mas não porque algum script saiu: não havia nenhum. TBT mede tarefas longas na thread principal, de qualquer origem: parse do HTML, cálculo de estilo, layout, decodificação de imagem. Com o CPU 4× mais lento da simulação, algumas tarefas passam de 50 ms. Por isso “TBT ≈ 0” é uma evidência fraca sozinha; a Network é a evidência forte.

2. As trocas clássicas

Os quatro exemplos do plano da atividade. Os tamanhos são aproximados (versões recentes, minificado/gzip). Antes de citar num README, confira no arquivo real ou no bundlephobia.com.

jQuery → JavaScript nativo

~87 KB min · ~30 KB gzip → 0

com jQuery

$('.menu-btn').on('click', function () {
  $('#menu').toggleClass('aberto');
});
$.getJSON('/api/produtos', render);

nativo

document.querySelector('.menu-btn')
  .addEventListener('click', () =>
    document.getElementById('menu')
      .classList.toggle('aberto'));
fetch('/api/produtos').then(r => r.json()).then(render);

Moment.js → Intl.DateTimeFormat (ou date-fns)

~58 KB min · ~18 KB gzip, mais locales → 0

com Moment

import moment from 'moment';
import 'moment/locale/pt-br';
moment(pedido.data).format('LL');
// "21 de outubro de 2026"

nativo

new Intl.DateTimeFormat('pt-BR', {
  dateStyle: 'long'
}).format(new Date(pedido.data));
// "21 de outubro de 2026"

Bootstrap completo → só os módulos usados

CSS ~230 KB min · ~30 KB gzip

tudo

<link rel="stylesheet"
  href="bootstrap.min.css">
<script src="bootstrap.bundle.min.js"></script>
<!-- usa só grid, botões e navbar -->

só o necessário (Sass)

@import "bootstrap/scss/functions";
@import "bootstrap/scss/variables";
@import "bootstrap/scss/mixins";
@import "bootstrap/scss/grid";
@import "bootstrap/scss/buttons";
@import "bootstrap/scss/nav";

Font Awesome completo → SVG dos ícones usados

CSS ~100 KB + fonte ~150 KB → ~1 KB

fonte de ícones inteira

<link rel="stylesheet" href="all.min.css">
<i class="fa-solid fa-cart-shopping"></i>
<!-- baixa milhares de ícones para usar 3 -->

SVG inline

<svg width="20" height="20" viewBox="0 0 24 24"
     aria-hidden="true">
  <path d="M7 4h-2l-1 2h2l3.6 7.6..."/>
</svg>
O raciocínio é sempre o mesmo: quanto da biblioteca eu uso? O navegador já faz isso sozinho? Dá para importar só a parte usada? “Trocar” nem sempre é o melhor: às vezes é importar menos (tree-shaking, imports por módulo) ou carregar depois (defer, import dinâmico só quando o usuário clica).

3. Simulador: o peso das escolhas

Escolha, para cada necessidade, se o site usaria a versão pesada, a enxuta ou nada. O medidor mostra os bytes extras e o tempo só de download na rede do Lighthouse Mobile (~1,6 Mbit/s). Execução de JS não está incluída: o custo real é maior.

Valores aproximados (gzip). A base do Pet&Style é o index.html atual: ~5,8 KB com gzip, já com o CSS inteiro dentro. Repare que uma única lib “inocente” pode pesar 5× a página inteira.

4. Fontes web: a “biblioteca” que ninguém lembra

Fonte web também é dependência externa. Com Google Fonts, o caminho até o texto aparecer com a fonte certa tem várias etapas:

flowchart LR
  H["📄 HTML"] --> C["🔗 fonts.googleapis.com
DNS + TLS + CSS"]
  C --> W["🔗 fonts.gstatic.com
DNS + TLS + woff2"]
  W --> T["🔤 texto com a fonte"]
  H -.-> S["🔤 Pet&Style hoje
fonte do sistema, imediato"]
  style S fill:#0f9d58,color:#fff,stroke:#0f9d58
  style W fill:#e8a200,color:#000,stroke:#e8a200
Dois domínios novos, um CSS bloqueante e um arquivo por peso de fonte. Riscos: texto invisível enquanto a fonte baixa (FOIT) e salto de layout quando ela chega (CLS).

O Pet&Style usa a pilha padrão do Tailwind (font-sans: ui-sans-serif, system-ui, sans-serif, …). O navegador usa a fonte que já está instalada: zero requisições. É uma decisão de projeto boa, e o README deve dizer isso.

Se um dia o projeto precisar de uma fonte própria: hospede o woff2 junto do site, use só os pesos necessários, font-display: swap e <link rel="preload" as="font" type="font/woff2" crossorigin> para a fonte do texto principal.

5. Provando o “não se aplica” no DevTools

Três prints bastam. Faça na página servida (npx serve .), janela anônima, Network com Disable cache, recarregando com Ctrl+Shift+R.

Simulação com a lista do baseline (tag antes), tirada do relatório Lighthouse salvo em docs/relatorios/antes/. Clique nos filtros. O que importa no print é o rodapé: “0 / 9 requests” com o filtro JS.

📭Network → JS
Lista vazia. Rodapé: 0 / N requests. Prova que nenhum script é baixado.
🔤Network → Font
Lista vazia. Prova que não há fonte web.
📊Coverage
Nenhuma linha do tipo JS. Depois do CSS inline (fase 9), só o documento aparece, como CSS.
🔍Elements
Ctrl+F → <script → “0 of 0”. Prova no próprio HTML.
Cuidado com o Live Server e extensões: eles injetam scripts. Se o filtro JS mostrar algo como livereload.js ou content.js, o problema é o ambiente, não o site (lembra da fase 3?). Por isso: npx serve . e janela anônima.

6. A lista completa: auditoria network-requests do Lighthouse

O Lighthouse guarda a lista de todas as requisições numa auditoria chamada network-requests. Ela não aparece no relatório visual, mas está dentro do HTML salvo. É a evidência mais completa, porque mostra o tipo de cada recurso.

Como extrair

Abra um relatório salvo (por exemplo, docs/relatorios/antes/antes-mobile-1.report.html) no navegador → DevTools → Console → cole:

Console do DevTools, com o relatório aberto
console.table(__LIGHTHOUSE_JSON__.audits['network-requests'].details.items
  .map(i => ({ tipo: i.resourceType, url: i.url, kB: +(i.transferSize / 1024).toFixed(1), status: i.statusCode })))

8. Para o README

### Substituição de bibliotecas pesadas — não se aplica

A página não carrega nenhum JavaScript nem biblioteca externa, e usa a pilha de fontes
do sistema (`font-sans` do Tailwind): zero requisições de fonte.

Evidências (docs/relatorios/depois/):
- Network com filtro **JS**: 0 de N requisições (print `network-js.png`)
- Network com filtro **Font**: 0 de N requisições (print `network-font.png`)
- Lighthouse, auditoria `network-requests`: nenhum recurso do tipo Script ou Font;
  "JavaScript execution time" = 0,0 s

Observação: no "antes", o TBT Mobile não era zero (27 ms) mesmo sem JS, porque mede tarefas longas de
parse, estilo, layout e decodificação de imagens com a CPU 4× mais lenta da simulação.

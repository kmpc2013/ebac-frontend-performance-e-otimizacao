Por que não reescrever o histórico (git commit --amend + push --force) para sumir com o Next.js? Funciona, mas reescrever o que já foi publicado é um mau hábito: em um repositório compartilhado, quebra o trabalho de quem já baixou. Um commit novo, explicando a troca, é transparente e seguro. Mover uma tag também altera algo publicado, mas aqui é aceitável: ninguém mais usa o repositório, e a tag só tem valor se apontar para o lugar certo.

3. Passo a passo

Rode os comandos na raiz do projeto.

Revisar o que vai entrar no commit

terminal
$ git status

Esperado: os arquivos do Next.js como deleted, e index.html, src/, assets/ e as aulas novas em docs/aulas/ como novos ou modificados.

Sobre o .gitignore: ele saiu junto com o Next.js. O Pet&Style não tem node_modules nem build, então não precisa de um. Se quiser deixar docs/aulas/ fora do repositório público, crie um .gitignore com /docs/aulas/.

Commit da troca de projeto

terminal
$ git add -A
$ git commit -m "chore: troca o projeto base para o Pet&Style (baseline de performance)"

O -A inclui as remoções. Um git add . também funciona nas versões atuais do git, mas o -A deixa a intenção explícita.

Mover a tag antes

terminal
# apaga a tag antiga, local e remota
$ git tag -d antes
$ git push origin --delete antes

# cria a tag anotada no commit atual (o do Pet&Style)
$ git tag -a antes -m "Estado original do Pet&Style, antes das otimizações"

# envia o commit e a tag nova
$ git push origin main
$ git push origin antes

Opcional: antes de apagar, você pode guardar uma referência ao projeto antigo com git tag projeto-anterior 9d4951e. Não é necessário; o commit continua no histórico de qualquer forma.

Conferir

terminal
$ git log --oneline --decorate
$ git show antes --stat

Esperado: o commit novo com (HEAD -> main, tag: antes, origin/main), e o 9d4951e logo abaixo, sem tag. O git show antes --stat deve listar index.html, src/ e assets/. No GitHub, a aba Tags deve mostrar antes no commit novo.

5. Estratégia de commits: uma otimização por commit

O enunciado pede para “identificar quais mudanças trouxeram maior impacto”. Com um commit por otimização, cada ponto do histórico pode ser medido separadamente:

gitGraph
  commit id: "Next.js (descartado)"
  commit id: "Pet e Style original" tag: "antes"
  commit id: "perf hero"
  commit id: "perf produtos"
  commit id: "perf logo"
  commit id: "perf css minificado"
  commit id: "perf html minificado"
  commit id: "fix favicon e meta"
  commit id: "docs README" tag: "depois"
Histórico ideal. Depois de cada commit perf, uma medição rápida mostra quanto aquela mudança rendeu. Aposto que o “perf hero” vai ser o campeão.

1. Onde estamos

O projeto escolhido é este Next.js 16 (Retro Tech Digest). Um profissional experiente define as expectativas antes de começar, para não se frustrar nem prometer o que não pode entregar. A escala abaixo é uma previsão do quanto cada tipo de evidência vai mudar entre o “antes” e o “depois”:

Score do Lighthouse

Previsão didática, não medição. O projeto já é enxuto, então o score deve mudar pouco. A prova da melhoria vai estar nos números finos, e por isso eles precisam ser registrados desde o início.
Lembre do enunciado: “Não é obrigatório atingir uma pontuação específica no Lighthouse — o que é avaliado é o progresso relevante e documentado.” Nossa estratégia é exatamente essa.

2. Por que versionar antes de mexer

A pasta do projeto ainda não é um repositório git. Se você começar a otimizar agora, o estado original some e o relatório “antes” passa a ser só um print, sem como reproduzir. Com uma tag no commit inicial, você pode voltar a ele a qualquer momento:

flowchart LR
  A["📁 Projeto atual"] --> B["git commit
estado original"]
  B --> T(["🏷️ tag antes"])
  T --> C["Otimizações
commit a commit"]
  C --> D(["🏷️ tag depois"])
  T -. "git switch --detach antes
build + medir de novo" .-> M["📊 Comparação justa
mesma máquina, mesmo dia"]
  D -.-> M
  style T fill:#e8a200,color:#000,stroke:#e8a200
  style D fill:#0f9d58,color:#fff,stroke:#0f9d58
Dica de quem já errou muito: o Lighthouse muda com a máquina, o navegador, a bateria e até as abas abertas. Se você mediu o “antes” na segunda e o “depois” na sexta, a comparação já não é justa. Com a tag antes, na fase 10 dá para medir os dois estados na mesma sessão. Isso deixa o comparativo muito mais confiável.

3. Revisar o .gitignore antes do primeiro commit

O primeiro commit é o que mais faz gente subir lixo para o GitHub. Conferi o .gitignore deste projeto:

ItemSituaçãoPor que importa
/node_modules✅ ignoradoCentenas de MB; é recriado com npm install.
/.next/✅ ignoradoSaída do build; é recriada com npm run build.
.env*✅ ignoradoSegredos nunca vão para um repositório público.
package-lock.json✅ será versionadoGarante as mesmas versões das dependências no “antes” e no “depois”. Sem ele, a comparação perde valor.
task.html⚠️ ignorado em qualquer pastaVeja abaixo.

A última linha do .gitignore é task.html. Uma regra sem barra no início vale para qualquer pasta, então ela também ignora docs/task.html. Você tem duas opções:

# opção A: versionar o enunciado junto (recomendado, documenta o contexto)
- task.html
 
# opção B: ignorar só um task.html que esteja na raiz
- task.html
+ /task.html

Essa alteração é sua: o .gitignore fica fora de docs/.

Também decida se docs/aulas/ vai para o repositório público. É material de estudo, e o avaliador não precisa dele. Se preferir deixar de fora, adicione /docs/aulas/ ao .gitignore.

4. Passo a passo

Rode os comandos na raiz do projeto. O git e o gh (GitHub CLI) já estão instalados na sua máquina.

Confirmar que o projeto compila

Não faz sentido congelar um “antes” que não builda. A fase 3 vai medir exatamente este build.

terminal
$ npm install
$ npm run build

Ao final, o Next lista as rotas. Confira se /, /artigos e /artigos/[slug] aparecem como estáticas (○ ou ●). Anote essa saída, porque ela vai para o README.

Iniciar o repositório e revisar o que vai entrar

terminal
$ git init -b main
$ git status

Leia o git status com calma. node_modules e .next não podem aparecer. Se aparecerem, pare e revise o .gitignore.

Commit do estado original + tag antes

terminal
$ git add .
$ git commit -m "chore: estado original do projeto (baseline de performance)"
$ git tag -a antes -m "Estado original, antes das otimizações"

A opção -a cria uma tag anotada, que guarda autor, data e mensagem. É a recomendada para marcos importantes.

Criar o repositório público no GitHub e enviar

terminal
# confirme que está logado (se não estiver: gh auth login)
$ gh auth status

# cria o repo público, liga o remote "origin" e faz o push da main
$ gh repo create ebac-frontend-performance --public --source=. --remote=origin --push

# tags não sobem com o push normal, é preciso enviar explicitamente
$ git push origin --tags

Prefere o site? Crie o repositório vazio em github.com/new (sem README, sem .gitignore) e rode git remote add origin <url>, git push -u origin main e git push origin --tags.

Conferir

terminal
$ git log --oneline --decorate
$ git tag -n

Saída esperada: um commit com (HEAD -> main, tag: antes, origin/main). No GitHub, a aba Tags deve mostrar antes.

5. Estrutura de pastas da entrega

A organização é um dos critérios de avaliação. Esta é a estrutura que vamos construir ao longo das fases (em verde o que é novo):

ebac-frontend-performance/ ├── app/ # código (você otimiza aqui) ├── data/ ├── lib/ ├── public/ # SVGs mortos saem na fase 7 ├── docs/ │ ├── task.html # enunciado │ ├── plan.json # plano de estudos │ ├── aulas/ # material de estudo (opcional no repo) │ └── relatorios/ │ ├── antes/ # fase 3: relatório + prints do baseline │ └── depois/ # fase 10: relatório + prints finais ├── node_modules/ # ignorado ├── .next/ # ignorado ├── package.json ├── package-lock.json └── README.md # reescrito na fase 11
O git não versiona pastas vazias. Se quiser subir docs/relatorios/antes/ e depois/ já agora, coloque um arquivo vazio .gitkeep em cada uma. Ou crie as pastas só quando houver relatórios para guardar, na fase 3.

6. Estratégia de commits: uma otimização por commit

A fase 9 do enunciado pede para “identificar quais mudanças trouxeram maior impacto”. Se tudo entrar num commit só, você não consegue separar o efeito de cada mudança. Com um commit por otimização, cada ponto do histórico pode ser medido:

gitGraph
  commit id: "estado original" tag: "antes"
  commit id: "perf fontes"
  commit id: "perf body after"
  commit id: "perf transicoes"
  commit id: "chore remove SVGs"
  commit id: "fix metadata e lang"
  commit id: "docs README" tag: "depois"
Histórico ideal. Depois de cada commit perf, uma medição rápida mostra quanto aquela mudança rendeu.

Use o padrão Conventional Commits nas mensagens. Recrutadores e avaliadores leem o histórico:

PrefixoQuando usarExemplo
perf:Mudança cujo objetivo é performanceperf: limita pesos da Space Grotesk a 400 e 700
chore:Manutenção sem efeito no comportamentochore: remove SVGs não utilizados de public/
fix:Correção de algo erradofix: define lang pt-BR e metadata do site
docs:Só documentaçãodocs: adiciona comparativo antes/depois ao README

1. As três alavancas de uma imagem

Na fase 4 você viu que o hero.jpg tinha três problemas somados. Cada um é uma alavanca diferente, e elas se multiplicam:

📐

Dimensão

Não baixar mais pixels do que a tela vai mostrar (considerando o DPR). 1200×1800 para exibir 380×256 é desperdício puro.

🧪

Formato

AVIF e WebP comprimem bem mais que JPG com a mesma qualidade visual. Mesmos pixels, menos bytes.

✂️

Proporção

A foto era retrato num espaço paisagem. O object-cover jogava fora mais da metade da altura. Recortar antes evita baixar o que vai ser cortado.

Por que 3:2? No celular do Lighthouse, o hero aparece com 380×256 px CSS: 380 ÷ 256 ≈ 1,48, praticamente 3:2 (1,5). Os cards de produto (h-48) são ainda mais largos que altos, e o object-cover continua cuidando do ajuste fino.

2. O script que gera as imagens

Dá para fazer tudo à mão no Squoosh: são 6 imagens. Mas aqui são 23 arquivos (5 imagens × larguras × 2 formatos, mais o logo). À mão, isso vira erro de digitação. Com um script, qualquer pessoa regera tudo com um comando e chega ao mesmo resultado.

scripts/images.mjs (trecho)
const TAG = 'antes';
const PROPORCAO = 3 / 2; // recorte paisagem

const IMAGENS = [
  { origem: 'assets/produtos/hero.jpg',    destino: 'assets/produtos/hero',    larguras: [480, 800, 1080] },
  { origem: 'assets/produtos/caminha.jpg', destino: 'assets/produtos/caminha', larguras: [400, 800] },
  // ... brinquedo, coleira, roupinha
];

const lerOriginal = (caminho) => execFileSync('git', ['show', `${TAG}:${caminho}`], { maxBuffer: 1 << 26 });

for (const { origem, destino, larguras } of IMAGENS) {
  const original = lerOriginal(origem);
  for (const largura of larguras) {
    const altura = Math.round(largura / PROPORCAO);
    const base = sharp(original).resize(largura, altura, { fit: 'cover', position: 'centre' });
    await base.clone().avif({ quality: 50, effort: 6 }).toFile(`${destino}-${largura}.avif`);
    await base.clone().webp({ quality: 75, effort: 6 }).toFile(`${destino}-${largura}.webp`);
  }
}

// Logo: exibido em 36x36, então 72x72 cobre telas 2x.
await sharp(lerOriginal('assets/logo.png')).resize(72, 72).webp({ quality: 85 }).toFile('assets/logo-72.webp');
DecisãoPor quê
git show antes:…Os originais saíram do repositório (commit 5c53e6c), mas continuam guardados na tag antes. O script lê de lá: sempre parte do original, nunca de uma cópia já comprimida. Recomprimir uma imagem já comprimida acumula perda.
fit: 'cover'Faz o recorte 3:2 pelo centro, igual ao que o object-cover fazia na tela.
avif quality 50 / webp quality 75As escalas de qualidade não são comparáveis entre formatos. AVIF 50 e WebP 75 dão qualidade visual parecida. Sempre confira o resultado com os próprios olhos, lado a lado (o Squoosh é ótimo para isso).
effort: 6Mais tempo de CPU na hora de gerar, arquivo menor. Custa segundos no build, e o ganho vale para todo visitante.
Larguras 480/800/1080 e 400/800Vêm do layout (seção 5): o hero chega a 540 px CSS, então 1080 cobre telas 2×. Os cards chegam a ~380 px no celular, e 800 cobre DPR até ~2.

Escolha uma imagem e veja quanto cada combinação de formato e largura pesa. Os números são os arquivos reais do projeto.

Repare no brinquedo: o original já tinha 800×533, a mesma proporção e quase a mesma largura do arquivo novo. Ali só mudou o formato, e o ganho foi de ~2,4×. Na caminha, mudaram dimensão, proporção e formato, e o ganho passou de 6×. As alavancas se multiplicam.

4. <picture>: oferecer formatos, deixar o navegador escolher

Nem todo navegador entende AVIF. O <picture> resolve isso sem JavaScript: o navegador lê os <source> em ordem e usa o primeiro cujo type ele suporta. Se nenhum servir, usa o <img>.

src/index.html: o hero
<picture>
  <source type="image/avif"
          srcset="assets/produtos/hero-480.avif 480w, assets/produtos/hero-800.avif 800w, assets/produtos/hero-1080.avif 1080w"
          sizes="(min-width: 1152px) 540px, (min-width: 768px) calc(50vw - 36px), calc(100vw - 32px)">
  <img src="assets/produtos/hero-800.webp"
       srcset="assets/produtos/hero-480.webp 480w, assets/produtos/hero-800.webp 800w, assets/produtos/hero-1080.webp 1080w"
       sizes="(min-width: 1152px) 540px, (min-width: 768px) calc(50vw - 36px), calc(100vw - 32px)"
       width="1080" height="720" fetchpriority="high"
       alt="Cães estilosos usando acessórios Pet&Style"
       class="w-full h-64 sm:h-80 md:h-96 object-cover rounded-2xl shadow-lg">
</picture>

Mesmo quando o AVIF é escolhido, quem aparece na tela é o <img>. Por isso alt, class, width/height, loading e fetchpriority ficam só no <img>. O <source> só troca o arquivo.
Decisão consciente: o fallback é WebP, não JPG. O WebP funciona em todos os navegadores atuais; um JPG extra só serviria a navegadores muito antigos e dobraria os arquivos a manter. Se o seu público tiver navegadores antigos (sistemas legados, por exemplo), acrescente um JPG no <img> e mova o WebP para um segundo <source>.

5. srcset e sizes: a conta que ninguém explica

O srcset com w diz ao navegador quais arquivos existem e a largura real de cada um. Mas o navegador escolhe o arquivo antes de calcular o layout: ele ainda não sabe que o hero vai ocupar meia tela. O sizes é a resposta que você dá a ele: “nesta largura de tela, a imagem vai ocupar tantos pixels CSS”.

O sizes não é chute: ele sai das classes do layout. O container do hero é:

  <div class="flex-1 text-center md:text-left"> ...texto... </div>
  <div class="flex-1 w-full"> ...picture... </div>
</div>

O navegador lê as condições do sizes da esquerda para a direita e para na primeira verdadeira. Por isso a maior min-width vem primeiro, e o último valor (sem condição) é o padrão.

E os cards de produto?

Mesmo raciocínio, com o grid grid-cols-1 sm:grid-cols-2 lg:grid-cols-4 gap-6 (24 px de vão) dentro de um container max-w-6xl com px-4:

Simplificação honesta: entre 1024 e 1151 px, o card é um pouco menor que 262 px (o container ainda não chegou ao máximo). Dizer 262 superestima um pouco, então o navegador nunca escolhe uma imagem pequena demais. Errar para cima é o lado seguro.
DPR de novo: o navegador multiplica o valor do sizes pelo DPR da tela e procura no srcset um arquivo com pelo menos essa largura. O Lighthouse Mobile emula um Moto G Power: tela de 412 px e DPR 1,75. O hero fica com 412 − 32 = 380 px CSS; 380 × 1,75 = 665 px reais. O menor candidato com pelo menos 665 px é o 800w. Teste na calculadora abaixo.

7. Prioridade e lazy loading: quem baixa primeiro

Arquivo menor resolve a load duration do LCP. Mas na fase 4 vimos outro problema: o hero disputava banda com as 4 fotos de produto. Três atributos resolvem isso:

AtributoOndeO que faz
fetchpriority="high"só no heroAvisa o navegador, já na leitura do HTML, que esta imagem é a mais importante. Sem ele, imagens costumam começar com prioridade baixa e só sobem depois que o layout mostra que estão visíveis. Ataca o load delay do LCP.
loading="lazy"só nos produtosAdia o download até a imagem se aproximar da área visível. No celular, os produtos estão abaixo da dobra: deixam de disputar banda com o hero.
decoding="async"só nos produtosPermite decodificar a imagem fora do caminho da pintura. Ganho pequeno, custo zero.
width + heighttodasO navegador calcula a proporção (aspect-ratio) e reserva o espaço antes de a imagem chegar: evita CLS. Aqui as classes h-64/h-48 já fixavam a altura, mas os atributos protegem contra mudanças futuras no CSS. Use a proporção do arquivo (1080×720, 800×533), não o tamanho exibido.
Nunca coloque loading="lazy" no LCP. Imagem lazy só começa a baixar depois que o navegador calcula o layout e descobre que ela está na tela. No hero, isso aumenta o load delay e piora o LCP: é o erro mais comum desta fase. O logo também está no topo: sem lazy.

9. Conferir no DevTools

  1. Rode npx serve . e abra em janela anônima, com o DevTools em modo dispositivo (Ctrl+Shift+M) simulando 412 px e DPR 1,75 (em Dimensions: Responsive, menu ⋮ → Add device pixel ratio).
  2. Network → Img, com Disable cache. Recarregue. Confira a coluna Type (avif), a Priority do hero (High) e quais produtos vieram.
  3. Console: digite $$('img').map(i => i.currentSrc). O currentSrc mostra o arquivo que o navegador de fato escolheu, e não o src escrito no HTML.
  4. Mude a largura e o DPR, desative o cache e recarregue. Os arquivos escolhidos batem com a calculadora?
Pegadinha: se você aumenta a tela sem recarregar, o navegador pode trocar para um arquivo maior; se diminui, ele costuma manter o maior que já tem em cache. Para testar a escolha, sempre recarregue com o cache desativado.

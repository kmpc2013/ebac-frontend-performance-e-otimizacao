1. O objetivo: uma comparação que ninguém consiga contestar

Um avaliador desconfiado vai perguntar três coisas sobre o seu “antes × depois”:

  1. “Foi medido do mesmo jeito?” Mesma ferramenta, mesma versão, mesmo servidor, mesmos presets, mesma máquina, mesmo número de execuções. Senão, você está comparando ambientes, não código.
  2. “O que causou o quê?” Se todas as mudanças foram medidas de uma vez, ninguém sabe se o LCP caiu por causa das imagens ou da minificação.
  3. “Isso não é sorte?” Uma execução boa por acaso não prova nada. Por isso, 3 execuções e a mediana.

Como medir versões antigas sem bagunçar a pasta de trabalho

O plano sugeria git switch --detach antes. Funciona, mas troca os arquivos da sua pasta de trabalho, e na tag antes nem existe o scripts/medir.mjs (ele entrou no commit 6c8bd63). Aqui foi usado git archive: ele extrai uma versão para outra pasta, e o script atual mede essa pasta.

Git Bash · na raiz do projeto
# 1. Extrair cada versão para uma pasta fora do projeto
$ mkdir -p ../medir/antes ../medir/depois
$ git archive antes | tar -x -C ../medir/antes
$ git archive HEAD  | tar -x -C ../medir/depois

# 2. Medir uma pasta por vez, com o MESMO script (PORTA: ver seção 5)
$ PORTA=3010 node scripts/medir.mjs ../medir/antes  docs/relatorios/antes  antes
$ PORTA=3010 node scripts/medir.mjs ../medir/depois docs/relatorios/depois depois

No PowerShell, troque PORTA=3010 node … por $env:PORTA = '3010'; node …. O git archive extrai só o que está commitado: por isso o index.html gerado pelo build fica no repositório. Se ele não estivesse, você precisaria rodar npm run build dentro de cada pasta extraída.

O total é quase o mesmo, mas agora sem nenhum recurso bloqueando a renderização. Variação pequena precisa de explicação, não de pânico.

4. Ruído: por que 3 execuções e a mediana

O Lighthouse do Mobile carrega a página sem limitar a rede e depois simula um celular com 4G lenta e CPU 4× mais lenta. Essa simulação usa os tempos de CPU que a sua máquina mediu de verdade. Se o antivírus, o navegador ou a temperatura do processador atrapalharem uma execução, ela sai diferente. Isso é ruído: variação que não vem do código.

As 3 execuções de cada lote, lado a lado

✅ Sinal

  • O LCP de cada lote varia ~50 ms entre execuções. A queda das imagens foi de 2.340 ms: quase 50× o ruído.
  • Existe um mecanismo: o hero passou de 160,6 KB para 18,3 KB e deixou de dividir a banda.
  • O número muda de patamar no commit que tem a causa, e fica lá.

❌ Ruído

  • O TBT mediano oscilou de 27 a 170 ms entre as etapas (execuções isoladas de 0 a 210 ms) numa página sem nenhum JavaScript.
  • O score ficou entre 98 e 100 nas etapas intermediárias, puxado justamente por esse TBT.
  • Nenhum commit explica a subida: minificar CSS não cria trabalho na thread principal.
Por que mediana e não média? Veja o Speed Index da etapa 3: 1,26 · 1,17 · 3,49 s. A média seria 1,97 s, puxada por uma execução estranha. A mediana (1,26 s) ignora o ponto fora da curva. Com 3 execuções, a mediana é simplesmente o valor do meio depois de ordenar, que é o que o medianaPorMetrica() do medir.mjs faz.
Ruído entre lotes também existe. As 3 execuções da etapa 3 deram FCP 0,90 · 0,89 · 0,92 s e as do final 0,70 · 0,67 · 0,68 s. Cada lote é bem estável, e mesmo assim a diferença entre eles (0,22 s) é do mesmo tamanho dos 0,26 s que o mesmo código variou entre a fase 3 e a fase 10. Como a última etapa só trocou cores e removeu uma regra CSS, não há mecanismo para o FCP cair. Conclusão honesta: LCP e peso são os números robustos; o FCP melhorou, mas com menos confiança, e não deve ser creditado ao contraste. É isso que a frase “o que se move de forma consistente é o LCP e o peso” do README quer dizer.

5. Caso real: a medição que deu certo demais

Isto aconteceu neste projeto, e é a lição mais importante da fase. Na primeira rodada de medições das etapas, todas saíram idênticas: o mesmo peso de 98,8 KB, os mesmos scores. E a etapa “+ CSS inline, favicon, meta”, que ainda não tinha o commit do contraste, mostrava Acessibilidade 100.

Isso é impossível: sem a troca de orange-500 por orange-700, a auditoria color-contrast tem que reprovar. Um número impossível significa que a página medida não era a que eu achava.

O script iniciava o próprio serve com stdio: 'ignore' (sem mostrar a saída) e esperava a porta 3000 responder. Ela respondia, mas quem respondia era o servidor antigo, servindo a pasta de trabalho, que já tinha o código final.

A correção: falhar alto em vez de medir errado

git show 40c13bf -- scripts/medir.mjs (trechos)
-const URL = 'http://localhost:3000/';
+const PORTA = process.env.PORTA ?? '3000';
+const URL = `http://localhost:${PORTA}/`;

+// Se já houver algo na porta, mediríamos a página errada sem perceber.
+if (!soResumir && (await responde())) throw new Error(`A porta ${PORTA} já está em uso: feche o servidor ou use PORTA=<outra>`);

-const servidor = ... spawn('npx', ['serve', resolve(raiz), '-l', '3000', ...]);
+const servidor = ... spawn('npx', ['serve', resolve(raiz), '-l', PORTA, ...]);

Com a proteção, todas as medições (antes, etapas e depois) foram refeitas na porta 3010, na mesma sessão. Aí os números passaram a fazer sentido: Acessibilidade 94 até a etapa 3 e 100 só no final; 9 requisições até a minificação e 8 depois do favicon. O ambiente.txt registra a porta usada e o motivo.

Desconfie de resultados bons demais ou iguais demais. Sinais de alerta:
  • versões diferentes do código com peso idêntico até a casa decimal;
  • um score que melhora antes do commit que deveria melhorá-lo;
  • uma auditoria aprovada sem o código que a corrige.
Antes de comemorar, confira o que foi medido: no relatório, a URL e o elemento LCP (o “antes” tem que mostrar hero.jpg; o “depois”, hero-800.avif) e, na lista de requisições, os arquivos que você espera.

Pegadinha da fase 3, de novo: esses tempos são observados no carregamento real, sem limitação de rede, em localhost. Por isso somam 682 ms enquanto o LCP do relatório é 3,66 s, que é o valor simulado para o celular com 4G lenta. Use o breakdown para ver quais fases encolheram, não para tirar o tamanho do LCP.
  • Load duration 48 → 5 ms: o hero baixado passou de 160,6 KB para 18,3 KB.
  • Load delay 27 → 9 ms: o download do hero começa praticamente junto com o HTML. É o número que justificou não usar preload (fase 9).
  • Render delay 587 → 145 ms: o tempo entre a imagem chegar e ser pintada. Contribuíram o fim do CSS bloqueante (inline agora) e uma imagem com ~5× menos pixels para decodificar (1200×1800 → 800×533).

O lazy loading do Chromium não espera a imagem entrar na tela: ele começa a baixar quando ela fica a uma margem de distância da área visível (da ordem de 1.250 px em conexões rápidas, maior em conexões lentas). Na tela do celular simulado, a seção de produtos está logo abaixo do hero, dentro dessa margem, então as fotos baixam no carregamento. O ganho real aparece em outras colunas:

  • Prioridade: de High para Low. Antes elas disputavam a banda com o hero; agora o hero termina (17 a 22 ms) antes de elas começarem (50 ms).
  • Tamanho: 288 KB → 71 KB, pelo AVIF e pelo recorte certo.
  • Numa página longa, com produtos a vários milhares de pixels da dobra, o lazy também economizaria bytes no primeiro carregamento. Aqui, não. Escreva isso no README em vez de prometer economia de bytes que a medição não mostra.

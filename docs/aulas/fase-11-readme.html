2. A espinha: gargalo → ação → resultado

Um README de otimização não é um diário (“primeiro fiz isso, depois aquilo”). É um argumento: havia um problema medido, foi feita uma mudança específica, e a mesma medição mostra o efeito. Cada gargalo ganha um código (G1…G7) que aparece nas três partes, para o leitor seguir o fio.

3. Seção por seção, com trechos reais

1. Projeto e stack

o que é? onde está?
README.md (trecho real)
- HTML estático + **Tailwind CSS v4.3** (CLI), sem JavaScript e com fontes do sistema.
- O estado original está congelado na tag [`antes`](../../tree/antes).

posso confiar?

| Ferramenta | Lighthouse 13.5.0 (CLI), categorias Performance, Acessibilidade, Boas práticas e SEO |

Por que existe: sem esta seção, todo número do README é “confia em mim”. Ela responde às três perguntas da fase 10 (mesmo jeito? mesma sessão? não é sorte?) e linka o script que gerou tudo. A nota sobre os relatórios do Live Server mostra que você sabe por que descartou uma medição.

4. Melhorias aplicadas

o que mudou? onde?
README.md (trecho real)
### 4.1 Imagens (G1, G2, G3) — commit `3a1813f`
...
- **Hero:** ... Tem `width`/`height` e `fetchpriority="high"`, e **não** usa `loading="lazy"`, porque é o LCP.
...
- **Preload do LCP não foi usado:** o `<img>` do hero já está no HTML inicial com `fetchpriority="high"`.
  No relatório final, o *resource load delay* do LCP é de 9 ms, então não há o que antecipar.

Por que existe: o título já diz quais gargalos resolve e qual commit conferir. Cada decisão tem o porquê junto (“não usa lazy, porque é o LCP”). E uma otimização não feita também é documentada, com o número que justifica a decisão.

5. Comparativo antes × depois

funcionou? por causa de quê?
README.md (trecho real)
| Etapa | Score | FCP | LCP | Peso |
|---|---|---|---|---|
| Antes | 90 | 1,11 s | 3,66 s | 462,4 KB |
| + Imagens | 100 | 1,01 s | **1,32 s** | **98,8 KB** |
...
As variações de score e TBT entre 98 e 100 nas etapas intermediárias ficam dentro do ruído
entre execuções. O TBT oscilou de 27 a 170 ms sem relação com as mudanças. O que se move
de forma consistente é o LCP e o peso.

Por que existe: é a ponta “resultado”. As tabelas Mobile e Desktop dão o quanto; a tabela por etapa dá o por causa de quê. O parágrafo de ruído é o que separa um README de iniciante de um profissional: ele diz quais números não significam nada.

6. Conclusão

o que aprendi?
README.md (trecho real)
- **O que mais pesou foram as imagens.** Sozinhas, elas levaram o LCP Mobile de 3,66 s para 1,32 s ...
- **A minificação teve ganho real, mas pequeno.** Como o servidor já comprimia com gzip,
  minificar economizou menos de 1 KB na rede.

**Próximos passos:**
- publicar no GitHub Pages e conferir os dados de campo no PageSpeed Insights;

Por que existe: transforma tabelas em aprendizado, em ordem de impacto. Note a honestidade sobre o ganho pequeno, e que o que não foi medido (dados de campo) aparece em “próximos passos”, não como resultado.

4. O fio da evidência: seguindo o G1 pelo README

Teste de qualidade: escolha um gargalo e procure-o nas três seções. Se o fio arrebentar em algum ponto (o gargalo some, ou o resultado mede outra coisa), o argumento tem um buraco.

seção 3 · gargaloG1: hero.jpg 1200×1800, 160 KB, exibido em 540×384 no máximo. Afeta LCP, Speed Index e peso.
seção 4.1 · açãoRecorte 3:2, AVIF/WebP 480/800/1080 com srcset, fetchpriority="high". Commit 3a1813f. Tabela: hero 160,6 KB → 18,3 KB.
seção 5 · resultadoLinha “+ Imagens”: LCP 3,66 → 1,32 s e peso 462,4 → 98,8 KB, no commit que contém a ação.
A métrica prometida no gargalo (LCP) é a mesma conferida no resultado, e a variação aparece na etapa certa. Faça o mesmo exercício com G6 (favicon e meta → Boas práticas e SEO 100 na etapa do bônus) e G7 (contraste → Acessibilidade 100 só no final).

5. Links relativos para os relatórios

Evidência que o leitor não consegue abrir não é evidência. Todo número do README aponta para o arquivo de onde saiu, com link relativo ao próprio README.md. Assim os links funcionam no GitHub, num fork, num repositório renomeado e no clone de qualquer pessoa.

No READMENo GitHub, abre
[resumo](docs/relatorios/antes/resumo.md)github.com/USUARIO/REPO/blob/main/docs/relatorios/antes/resumo.md (renderizado)
[antes/](docs/relatorios/antes/)a listagem da pasta (…/tree/main/docs/relatorios/antes)
[scripts/medir.mjs](scripts/medir.mjs)o código do script
[antes](../../tree/antes)github.com/USUARIO/REPO/tree/antes: o repositório inteiro na tag
[Metodologia](#2-metodologia-de-medição)a âncora do título na mesma página

Três detalhes que pegam muita gente

  • ../../tree/antes: o GitHub exibe o README como se estivesse em /USUARIO/REPO/blob/main/README.md. Subir dois níveis (../../) sai de blob/main e chega em /USUARIO/REPO/; dali, tree/antes é a rota do GitHub para a tag. Funciona no GitHub, mas não na prévia do VS Code, onde não existe essa rota.
  • Âncoras: o GitHub gera o id do título em minúsculas, troca espaços por - e remove pontuação, mas mantém os acentos. “5. Comparativo antes × depois” vira #5-comparativo-antes--depois: o × some e sobram dois hífens. Na dúvida, passe o mouse no título renderizado e copie o link do ícone 🔗.
  • Relatórios .html: no GitHub, um .report.html abre como código, não como página. Para ver renderizado, baixe o arquivo ou abra pelo GitHub Pages (fase 9): https://USUARIO.github.io/REPO/docs/relatorios/depois/depois-mobile-2.report.html. Por isso o README linka as pastas e o resumo.md, que o GitHub renderiza.

❌ Não funciona para mais ninguém

  • C:\Users\voce\Projetos\...\resumo.md
  • http://localhost:3000/docs/...
  • file:///...

✅ Funciona em qualquer lugar

  • docs/relatorios/depois/resumo.md
  • scripts/medir.mjs
  • #5-comparativo-antes--depois

Links absolutos para https://github.com/…/blob/main/… funcionam, mas quebram se o repositório for renomeado ou copiado. Prefira os relativos.

6. O que evitar

EvitePor que enganaEscreva assim
Print sem contexto: um círculo verde “100” colado no README.Mobile ou Desktop? Qual execução? Antes ou depois do quê? Um print de 100 no Desktop não diz nada: o “antes” já era 100 lá.Tabela com medianas e link para os relatórios. Se usar print, legenda completa: “Lighthouse 13.5.0, Mobile, execução mediana (depois-mobile-2), 21/10”. O print mais útil costuma ser o da Network mostrando a prioridade, que a tabela não mostra.
Número sem método: “o LCP caiu para 1,2 s”.Medido onde? Uma vez só? Com o mesmo throttling do antes?“Medianas de 3 execuções … ‘Antes’ e ‘depois’ medidos na mesma sessão e com o mesmo script.” (seção 2 do README)
Prometer o que não mediu: “o site ficou 3× mais rápido para os usuários”.Você mediu laboratório, com celular simulado. Não há dados de campo de um site recém-publicado.“LCP Mobile (Lighthouse, simulado) 3,66 → 1,21 s.” Os dados de campo vão para os próximos passos, como no README.
Adjetivo no lugar de número: “a minificação deixou o site muito mais leve”.“Muito” não pode ser conferido, e aqui nem é verdade.“Como o servidor já comprimia com gzip, minificar economizou menos de 1 KB na rede.”
Creditar o ruído: “o CSS inline zerou o TBT”.O TBT oscilou de 27 a 170 ms sem relação com as mudanças.“O que se move de forma consistente é o LCP e o peso.”
Diário em vez de argumento: “depois tentei X, não deu, aí fiz Y…”.O leitor precisa reconstruir a lógica sozinho.Gargalo (G1) → ação (commit) → resultado (mesma métrica). Tentativas que ensinaram algo viram uma frase com o motivo (“preload não foi usado: load delay de 9 ms”).

    4. A frase reescrita
    
    
    **G1 — imagem do LCP superdimensionada.** O hero era um JPG 1200×1800 (160 KB) exibido
em no máximo 540×384 px (`assets/produtos/hero.jpg`). Gerei AVIF/WebP de 480, 800 e 1080 px
com `srcset`/`sizes` e `fetchpriority="high"` (commit `3a1813f`). Resultado: LCP Mobile
3,66 s → 1,32 s nessa etapa (mediana de 3 execuções, Lighthouse 13.5.0), hero baixado
160,6 KB → 18,3 KB.
    
    
    Repare no que entrou: qual imagem, quanto ela pesava e por que era demais, onde e em que commit foi corrigida, e a mesma métrica antes e depois, com o método. “Muito mais rápido” sumiu: o número fala sozinho.
    
    
    5. Prints
    
    
    Não é um problema: o README linka os relatórios completos, que contêm muito mais que um print, e as tabelas trazem os números exatos. O que conta é a evidência, não o formato. Um print acrescenta algo quando mostra o que a tabela não mostra: por exemplo, a aba Network antes e depois, com a coluna Priority (produtos em High → Low) e o waterfall do hero terminando antes dos produtos. Se usar, salve em docs/relatorios/ e escreva a legenda completa (ferramenta, Mobile ou Desktop, execução, data).

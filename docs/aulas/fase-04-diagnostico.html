1. O método: sintoma → hipótese → causa

Iniciante lê o relatório e sai mudando coisas. Profissional trata cada alerta como um sintoma, levanta uma hipótese e só aceita a causa depois de confirmar com uma segunda ferramenta.

Sintoma (o relatório diz)

“LCP de 4 s; no LCP breakdown, o load duration é a maior fatia.”
→

Causa (você prova)

“O LCP é o hero.jpg: 160 KB, 1200×1800 px, exibido em 380×256. A Network mostra o download dividindo a banda com as 4 fotos de produto.”

3. Quantos pixels estamos desperdiçando?

Para decidir o tamanho certo de uma imagem, entra um conceito novo: o DPR (device pixel ratio). Telas modernas têm mais pixels físicos que pixels CSS. O celular que o Lighthouse simula tem DPR 1,75: uma imagem exibida com 380 px CSS de largura precisa de 380 × 1,75 ≈ 665 px reais para ficar nítida.

Desenho em escala (15%). A foto é retrato, mas o espaço é paisagem: o object-cover corta mais da metade da altura. Esses pixels são baixados, decodificados e jogados fora.

Tamanhos exibidos calculados a partir das classes do index.html: o hero tem w-full com h-64 (256 px) no mobile e h-96 (384 px) no desktop; os produtos têm h-48 (192 px); o logo, 36×36. Confirme no Elements. No desktop, os produtos aparecem em 4 colunas, e o desperdício chega a ~18× nas fotos em retrato.

G1

LCPSpeed IndexKB
Onde

Evidência a procurar

G2

Fotos de produto: grandes e sem lazy loading

LCPKB
Onde
index.html, os 4 <img> dentro de #produtos: caminha.jpg, brinquedo.jpg, coleira.jpg e roupinha.jpg.
Evidência a procurar
Network: as 4 baixadas no carregamento inicial, com o waterfall sobreposto ao do hero. Improve image delivery listando cada uma.
Hipótese
No mobile, a seção de produtos começa abaixo da dobra; o hero ocupa a primeira tela. Sem loading="lazy", o navegador baixa as 4 imediatamente. Além disso, são 2× a 4× maiores que o necessário.
Como confirmar
Experimento no DevTools, sem mexer no código: Network → clique com o botão direito em caminha.jpg → Block request URL. Faça o mesmo com as outras 3 e rode o Lighthouse Mobile de novo. Se o LCP cair, a disputa de banda está provada. Depois, desbloqueie (Network request blocking → desmarcar).

KBganho pequeno
Onde

G4

CSS bloqueante e sem minificar

FCPKB
Onde
src/output.css (16,9 KB; ~3,8 KB com gzip), gerado pela CLI do Tailwind a partir de src/input.css.
Evidência
Render-blocking requests listando o output.css. Abra o arquivo: tem indentação, quebras de linha e o comentário de licença. Dentro de :root, --color-amber-600 e --color-blue-300 não são usados por nenhuma regra.
Hipótese
Todo CSS no <head> bloqueia a primeira pintura, e é assim que deve ser. Não dá para eliminar o bloqueio, mas dá para encolher o arquivo. O ganho vai ser modesto: com gzip, a diferença é de poucos KB.
Armadilha da Coverage
A Coverage vai mostrar parte do CSS como “não usado”. Boa parte disso são variantes como sm:, md:, lg: e hover:, que não se aplicam naquela largura de tela ou ainda não aconteceram. Não é código morto.
⚠️ Para a fase 6
O Tailwind v4 varre automaticamente os arquivos do projeto atrás de classes. Agora existem os HTMLs de docs/aulas/, cheios de classes. Se você regerar o CSS sem excluir docs/, ele pode engordar. Vamos tratar disso na fase 6.

As perguntas do “Para eu corrigir”

  • Prioridade: hero High; caminha, brinquedo e coleira High; roupinha Medium. O hero não se destaca das fotos de produto, e é isso que o fetchpriority="high" resolve.
  • Experimento da G2: o resultado esperado é o LCP Mobile cair com os 4 produtos bloqueados, porque o hero passa a ter a banda simulada só para ele. O valor exato depende da sua execução: compare com os seus 3,66 s, sempre com mais de uma execução.
  • Hipótese refutada: a das classes CSS mortas (seção 1). Outra boa candidata: “o CSS bloqueante pesa no LCP”. A evidência mostra que ele é pequeno (4,1 KB) e chega antes das imagens; quem domina é o download do hero.
  • Conceitual (665 px): o celular simulado tem DPR 1,75: cada pixel CSS usa 1,75 pixel físico. 380 px CSS × 1,75 ≈ 665 px reais para a imagem ficar nítida. Servir 1200 px é baixar e decodificar ~7× mais pixels do que a tela consegue mostrar (e mais da metade da altura é cortada pelo object-cover). O caminho certo é oferecer várias larguras com srcset/sizes e deixar o navegador escolher a menor suficiente.

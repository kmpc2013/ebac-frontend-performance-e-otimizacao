Remoção de código morto

Código morto é tudo o que o navegador baixa (ou o repositório guarda) e ninguém usa. Hoje você aprende a provar o que está morto, a não confundir “não usado agora” com “nunca usado” e a apagar com segurança.

1. O que é (e o que não é) código morto

Na fase 4 eu suspeitei que o output.css estava cheio de classes mortas. A comparação mostrou que não: só sobravam 2 variáveis. Essa é a lição número um desta fase: “a Coverage marcou em vermelho” não é a mesma coisa que “está morto”.

2. Por que o Tailwind v4 já não gera classes não usadas

Em frameworks CSS “clássicos” (Bootstrap completo, por exemplo) você baixa tudo e usa 5%. O Tailwind faz o contrário: ele lê os seus arquivos, coleta todo texto que parece uma classe (os candidatos) e gera CSS só para os candidatos que existem no catálogo dele. Isso se chama geração sob demanda (o antigo modo “JIT”, que no v4 é o único modo).

  S["📄 src/index.html"] --> SC["🔍 Scanner
quebra o texto em tokens"]
  SC --> K["Candidatos
flex, text-orange-700,
md:h-96, Pet, Style..."]
  K --> F{"Existe utilitário
com esse nome?"}
  F -- "sim" --> G["🎨 Gera a regra
e as variáveis que ela usa"]
  F -- "não" --> X["Ignora em silêncio"]
  G --> O["src/output.css"]
  style O fill:#0f9d58,color:#fff,stroke:#0f9d58
O scanner não entende HTML: ele lê texto. Pet e Style também viram candidatos, mas não existe utilitário com esses nomes, então nada é gerado.

Consequência prática: não existe passo de “purge” para fazer. Se uma classe sai do HTML, ela sai do CSS no próximo build. Foi exatamente isso que aconteceu com as 2 variáveis:

git show antes:src/output.css (trecho do :root, antes da fase 6)
  --color-orange-500: oklch(70.5% 0.213 47.604);
  --color-orange-600: oklch(64.6% 0.222 41.116);
  --color-amber-600: oklch(66.6% 0.179 58.318);   ← nenhuma regra faz var(--color-amber-600)
  --color-blue-300: oklch(80.9% 0.105 251.813);    ← nenhuma regra faz var(--color-blue-300)

Por que elas existiam? O output.css original foi gerado com uma versão anterior do HTML, que tinha alguma classe amber-600/blue-300. O HTML mudou, o CSS não foi regerado, e as sobras ficaram. Ao regerar na fase 6, elas sumiram sozinhas. A mensagem do commit registra isso:

git show da893d7 --stat
perf(build): CSS do Tailwind e HTML minificados

- src/index.html passa a ser a fonte legível; o index.html da raiz é gerado por npm run build
- input.css com source(none) + @source "./index.html": docs/ fica fora da varredura
- output.css: 16,9 KB -> 13,5 KB (gzip 3,8 -> 3,5 KB); some o código morto
  (--color-amber-600 e --color-blue-300)
Lição de processo: código morto em projeto Tailwind quase sempre significa CSS gerado e esquecido (commitado sem build). A cura é ter o build como script (npm run build) e regerar sempre que o HTML mudar.

3. O risco inverso: varrer arquivos demais

Se o scanner lê texto, ele também lê texto que não é a sua página. No Tailwind v4, a detecção automática varre a pasta do projeto inteira (respeitando o .gitignore). Este repositório tem docs/aulas/*.html, cheios de palavras como grid, flex, hidden, block… Tudo isso viraria regra no output.css da loja.

❌ antes: src/input.css

@import "tailwindcss";

Varredura automática: o projeto inteiro, inclusive docs/.

✅ depois (da893d7)

@import "tailwindcss" source(none);

/* Só o HTML da página gera classes. */
@source "./index.html";

source(none) desliga a detecção automática; @source lista explicitamente o que pode gerar classes. O caminho é relativo ao input.css, por isso é ./index.html (o src/index.html).

Achado ao vivo: o scanner lê até comentários

Mesmo com a varredura restrita, o arquivo varrido inteiro conta. Rodando a comparação da próxima seção no código do commit 86429b4, apareceu uma regra que nenhum elemento usava:

src/output.css e src/index.html no commit 86429b4 (antes da correção)
/* output.css */
.flex{display:flex}.grid{display:grid}.inline{display:inline}.inline-block{...}

<!-- src/index.html, linha 14 (adicionado no commit 9f2c305) -->
<!-- No build, este link é trocado pelo CSS inteiro inline (ver scripts/build-html.mjs). -->

A palavra inline no comentário virou candidato, e inline é um utilitário válido do Tailwind (display: inline). Resultado: ~24 bytes de CSS morto, que entraram quando o CSS foi regerado no commit 86429b4. É insignificante em bytes, mas é um ótimo exemplo de como o mecanismo funciona e de por que a verificação precisa ser feita de novo a cada build.

Resolvido no commit 40c13bf: o comentário foi reescrito para “embutido numa tag style”, o npm run build regerou o CSS e .inline{display:inline} sumiu do output.css. Confira com git show 40c13bf -- src/index.html. Se a regra precisasse ficar fora mesmo com a palavra, o Tailwind v4 tem @source not inline("inline");, que bloqueia um candidato específico.

4. A prova: comparar seletores do CSS com as classes do HTML

A frase da fase 4, “todos os utilitários batem 1:1 com o HTML”, veio de um script simples. Ele não é parte do projeto; é uma ferramenta de investigação que você pode rodar de qualquer pasta:

comparar-css.mjs (ferramenta de diagnóstico, fora do projeto)
import { readFileSync } from 'node:fs';
const [htmlPath = 'src/index.html', cssPath = 'src/output.css'] = process.argv.slice(2);
const html = readFileSync(htmlPath, 'utf8');
const css = readFileSync(cssPath, 'utf8');

// 1. Todas as classes usadas em atributos class="..."
const usadas = new Set([...html.matchAll(/class="([^"]+)"/g)]
  .flatMap(m => m[1].trim().split(/\s+/)));

// 2. Todos os seletores de classe do CSS (.md\:h-96 vira md:h-96)
const regras = new Set([...css.matchAll(/\.((?:\\.|[A-Za-z_-])(?:\\.|[\w-])*)/g)]
  .map(m => m[1].replace(/\\(.)/g, '$1')));

// 3. Variáveis declaradas que nenhum var() lê
const vars = [...css.matchAll(/(--color-[\w-]+):/g)].map(m => m[1]);

console.log('no HTML sem regra:', [...usadas].filter(c => !regras.has(c)));
console.log('no CSS sem uso:', [...regras].filter(c => !usadas.has(c)));
console.log('variáveis sem var():', vars.filter(v => !css.includes(`var(${v}`)));

    6. Conferindo com a Coverage do DevTools

    A Coverage mostra, byte a byte, o que do CSS (e do JS) foi usado durante o carregamento. É a ferramenta que o enunciado espera ver, mas ela tem duas armadilhas que você precisa explicar no README.

    1. Abra a página servida (npx serve .) e o DevTools.
    2. Ctrl+Shift+P → digite Show Coverage → Enter.
    3. Clique no botão de recarregar dentro do painel (⟳ Start instrumenting coverage and reload page).
    4. Clique numa linha para abrir o arquivo no Sources: a barra à esquerda de cada regra fica verde (usada) ou vermelha (não usada).
    ConsoleNetwork

    Ilustração com “??” nos números de propósito: os valores são seus. As cores das regras no trecho de código são o padrão esperado numa tela de celular.

    Armadilha 1: variantes aparecem como “não usadas”

    No celular, md:flex-row não se aplica; no desktop, ela se aplica, mas aí sm:h-80 é sobrescrita… E hover:/focus: só “acontecem” com interação. Por isso a porcentagem não usada nunca chega a zero num CSS responsivo, e não deve. Para ver isso: ligue a Coverage, redimensione a janela, passe o mouse nos links e veja regras ficarem verdes (a Coverage continua gravando depois do carregamento).

    Armadilha 2: com CSS inline, a linha muda de nome

    Desde o commit 9f2c305 (fase 9), o CSS não é mais um arquivo baixado: ele vai dentro de um <style> no index.html. A Coverage então não mostra mais src/output.css; ela mostra o próprio documento (http://localhost:3000/) com tipo CSS, contando os bytes do bloco inline. Se você procurar output.css na lista e não achar, é isso.

    Como usar a Coverage no README: tire um print “antes” (tag antes) e “depois”, e escreva a interpretação: “a porcentagem não usada é composta por variantes responsivas e de estado; a comparação HTML × CSS confirma que não há utilitários sem uso”. Print sem interpretação não prova nada.

    ### Remoção de código morto

**CSS.** O Tailwind v4 gera CSS só para as classes encontradas nos arquivos varridos.
Ao regerar o `output.css` (commit da893d7), sumiram as 2 variáveis de tema sem uso

responsivas (`sm:`, `md:`, `lg:`) e de estado (`hover:`, `focus:`), que se aplicam em outras
larguras/interações. Print: docs/relatorios/depois/coverage.png

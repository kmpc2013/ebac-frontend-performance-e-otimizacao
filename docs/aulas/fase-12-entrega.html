3. Tornar o repositório público

Um repositório privado dá 404 para o corretor. Para o GitHub, “não existe” e “você não tem acesso” são a mesma página.

  1. No GitHub, abra o repositório → Settings (aba de engrenagem).
  2. Em General, role até o fim: Danger Zone → Change repository visibility → Change to public.
  3. Confirme digitando o nome do repositório.
  4. Teste de verdade: abra o link em uma aba anônima (Ctrl+Shift+N), sem login. Se o código aparecer, está público.
Antes de abrir para o mundo, procure segredos no histórico: tokens, senhas, arquivos .env. Tornar público expõe todos os commits, não só o último. Neste projeto não há nada sensível (é HTML, CSS e imagens), mas o hábito vale para a vida.

Também dá para conferir pelo terminal, sem login, pela API pública do GitHub:

terminal (Git Bash)
$ curl -s https://api.github.com/repos/kmpc2013/ebac-frontend-performance-e-otimizacao | grep visibility
  "visibility": "public",          ← privado responderia "Not Found"

4. Push dos commits e da tag antes

Hoje o seu repositório local está vários commits à frente do GitHub (ferramentas de medição, otimizações, relatórios, README e aulas; o número exato aparece no git status -sb). Já a tag antes foi recriada na fase 2 como tag anotada (objeto 6b4598d) no commit e852300 e enviada ao GitHub. Mesmo assim, confira: em outro clone, o remoto poderia estar com outra versão dela.

Passo 1: diagnosticar antes de mexer

Regra de ouro: nunca force nada sem antes olhar o que está do outro lado. O git ls-remote pergunta ao GitHub para onde as referências apontam, sem baixar nada:

terminal, na raiz do projeto
$ git status -sb
## main...origin/main [ahead N]
$ git rev-parse antes^{}
e852300bc999...                     ← a tag local aponta para o commit do Pet&Style
$ git ls-remote --tags origin antes
6b4598d8e8ad...  refs/tags/antes    ← o objeto da tag no GitHub
e852300bc999...  refs/tags/antes^{} ← o COMMIT para onde ela aponta
Como ler isso: uma tag anotada é um objeto próprio, com autor, data e mensagem, e tem um hash próprio (6b4598d). O sufixo ^{} significa “siga a tag até o commit”. Quem decide se a tag está certa é a linha ^{}, não a primeira. Ou seja: 6b4598d não é um commit, é o objeto da tag.

Passo 2: enviar a main

terminal
$ git push origin main
# "git push" não envia tags. Elas vão separadas, e de propósito.

Passo 3: a tag, conforme o diagnóstico

O ^{} do remoto mostra…SituaçãoO que fazer

Por que o --force é necessário (quando é)

Para o git, uma tag é um marco fixo: v1.0 deve significar sempre o mesmo código. Por isso, quando você tenta enviar uma tag com um nome que já existe no remoto apontando para outro lugar, o servidor recusa:

terminal
$ git push origin antes
 ! [rejected]        antes -> antes (already exists)
error: failed to push some refs
hint: Updates were rejected because the tag already exists in the remote.

# forçando SÓ a tag "antes" (nunca a main, nunca --tags)
$ git push --force origin antes

# versão mais segura: só força se o remoto ainda estiver no objeto que você viu no ls-remote
$ git push --force-with-lease=refs/tags/antes:6b4598d origin antes

Diferente de uma branch, a tag não “anda para frente”: não existe fast-forward de tag. Qualquer mudança nela é uma reescrita, e reescrita exige --force.

Cuidados com tags reescritas:
  • Quem já baixou a tag antiga continua com ela. Um git fetch comum não atualiza uma tag que já existe localmente. Cada clone teria que fazer git fetch --force --tags. Num time, isso gera confusão: duas pessoas, mesma tag, códigos diferentes.
  • Force só a referência certa. git push --force origin antes mexe em uma tag. git push --force sozinho mexe na branch; git push --force --tags reescreve todas as tags de uma vez. Evite os dois.
  • Anotada × leve. Se a sua tag local for leve (git cat-file -t antes responde commit) e a remota for anotada, forçar troca a anotada pela leve e perde a mensagem. Se for mesmo forçar, recrie antes como anotada: git tag -a -f antes e852300 -m "Estado original do Pet&Style, antes das otimizações".
  • Aqui é aceitável porque o repositório é só seu, ninguém depende dele e a tag só tem valor se apontar para o lugar certo (como discutimos na fase 2). Num projeto com releases públicas, o certo seria criar uma tag nova (antes-v2) em vez de reescrever.

Passo 4: confirmar

$ git status -sb

$ git ls-remote --tags origin antes

6. Publicar no GitHub Pages opcional

Não é obrigatório, mas dá ao corretor um link para ver o site funcionando sem clonar nada. Como o Pet&Style é estático e todos os caminhos são relativos (assets/…, sem barra no início), ele funciona direto na subpasta do Pages.

  1. No repositório: Settings → Pages.
  2. Source: Deploy from a branch. Branch: main, pasta / (root) → Save.
  3. Aguarde 1 a 2 minutos (aba Actions mostra o deploy). A URL fica no topo da página de Pages: https://kmpc2013.github.io/ebac-frontend-performance-e-otimizacao/.
  4. Abra a URL, confira o Console (sem 404) e coloque o link no README.
Não misture os números. Rodar o PageSpeed Insights na URL do Pages é um bom extra (é uma rede real, com CDN e HTTP/2), mas são outras condições. O comparativo oficial continua sendo o local, com o mesmo protocolo da fase 3. Se usar o PSI, apresente numa seção separada do README.

7. Enviar o link na plataforma EBAC

Envie o link do repositório (é o que o enunciado pede), não o do Pages. Se quiser, coloque os dois. Modelo de mensagem:

Repositório: https://github.com/kmpc2013/ebac-frontend-performance-e-otimizacao
Site publicado (opcional): https://kmpc2013.github.io/ebac-frontend-performance-e-otimizacao/

Projeto: landing page Pet&Style (HTML + Tailwind, sem JavaScript).
Código original na tag "antes"; versão otimizada na branch main.
Relatórios Lighthouse antes/depois em docs/relatorios/ e comparativo completo no README.
Depois de enviar, não mexa na main “só para ajustar uma vírgula” sem pensar: o corretor pode estar olhando. Se precisar corrigir algo, faça um commit pequeno e descritivo, nunca um push --force na main.
